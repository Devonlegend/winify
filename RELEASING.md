# Releasing Winify

Releases are automated from [Conventional Commits](https://www.conventionalcommits.org/)
by [release-please](https://github.com/googleapis/release-please). You never
create a tag or a release by hand.

## How a release happens

1. Land work on `main` with Conventional Commit messages (`feat:`, `fix:`, ...).
2. The **Release** workflow opens, or updates, a pull request titled
   `chore(main): release X.Y.Z`, containing the version bump and the new
   `CHANGELOG.md` section.
3. Review that pull request. Its changelog entry becomes the release notes.
4. Merge it. release-please creates the `vX.Y.Z` tag and the GitHub Release.
5. The same workflow builds the Windows and Linux binaries, writes their
   SHA-256 files, and attaches everything to the release.

The tag is created with the workflow's `GITHUB_TOKEN`, which by design does not
trigger another workflow run, so the build step runs in this same workflow
instead of on a tag push.

## Versioning

Semantic Versioning. While the project is pre-1.0, a breaking change bumps the
minor version rather than the major (`bump-minor-pre-major`).

| Commit | Bump |
| --- | --- |
| `fix:`, `perf:`, `refactor:` | patch: `0.1.1` |
| `feat:` | minor: `0.2.0` |
| `feat!:`, `fix!:`, or a `BREAKING CHANGE:` footer | minor while pre-1.0, major from 1.0 |

`docs`, `ci`, `chore`, `test`, and `build` do not trigger a release on their
own. When a release happens for another reason they are folded into it; `ci`,
`chore`, `test`, and `build` are hidden from the changelog entirely.

## The changelog

`CHANGELOG.md` is generated by release-please; do not hand-edit released
sections. Section titles and which commit types appear come from
`release-please-config.json` (`changelog-sections`).

## Forcing a version

Add a `Release-As: X.Y.Z` footer to any commit to make the next Release PR use
that exact version. You are never obliged to release: leave the Release PR open
and the next release just accumulates more changes.

## One-time setup

release-please opens pull requests, so the repository must permit it:

**Settings → Actions → General → Workflow permissions** → enable
**Allow GitHub Actions to create and approve pull requests**.

Because the Release PR is created with the default `GITHUB_TOKEN`, CI checks do
not run on it automatically. The change is only a version bump and a changelog
edit; if you want checks to run there too, add a personal access token as a
secret and pass it as the action's `token` input.
