# Setup Guide

The DevOps Control Center is a self-hosted deployment platform for environments
that mix Windows IIS and Docker. It connects directly to target servers over SSH
(Linux/Docker) and WinRM/PowerShell Remoting (Windows/IIS), builds and deploys
applications, fronts each deployment with a reverse proxy and automatic TLS, and
polls metrics over the same connections. A local assistant answers questions
from these guides plus live deploy and monitoring data.

## Prerequisites

- Go 1.27 or newer to build the control-center.
- A SQLite-backed data directory (created automatically).
- For Docker targets: SSH access with a private key, plus `git` and Docker
  (with the Compose plugin) on the target.
- For IIS targets: WinRM enabled on the target, an account that can stop
  services and recycle application pools, and `git` plus any build tooling.
- For automatic HTTPS: a running Caddy with its admin API reachable.
- Optional: ChromaDB and Ollama for the assistant.

## Build and run

    go build -o control-center ./cmd/control-center
    ./control-center serve -config config.yaml

Copy `config.example.yaml` to `config.yaml` and edit it. On first run a master
key is generated at `data/master.key` and the database is created. There is no
account yet, so the browser shows a **first-run registration page**. The default
listener is `127.0.0.1:8080`; the generated setup token is printed in the startup
log (the Windows installer prints it as well). Enter that token when creating the
admin username and password. The page closes as soon as the first account exists.

For headless or automated installs you can skip the browser step by setting
`CC_ADMIN_PASSWORD` (hashed at startup) or a pre-hashed
`auth.admin_password_hash` generated by `control-center hash-password`; the
account is then seeded on boot.

The default listen address is `127.0.0.1:8080`; change `server.addr` if that port
is in use. Set `proxy.public_ip` to the public address of the central Caddy host
when remote targets use generated or operator-managed domains.

## Managing servers and projects

The **Servers**, **Projects** and **Credentials** tabs manage the inventory from
the dashboard. The database is the source of truth; `servers.yaml` and
`projects.yaml` are imported only once, when the tables are empty (a fresh
install). After that you add and edit everything in the UI, and a **Deploy**
button on the Projects tab starts a deploy without waiting for a push.

## Credentials

Secrets are never stored in plaintext. Add an encrypted credential either from
the **Credentials** tab or with the CLI:

    control-center cred add server-002-ssh

Reference it from a server (`ssh_key_ref` for Docker, `credential_ref` for IIS)
and from a project (`webhook_secret_ref`). Credentials are decrypted only in
memory at connection time and are never logged or returned by any API response.
Project environment values are write-only in the UI and API; the editor shows
`[redacted]` and preserves existing values when the marker is submitted.

## Reverse proxy and TLS

Set `proxy.enabled: true` and point `proxy.admin_url` at Caddy's admin API. The
admin API is unauthenticated, so keep it on loopback (the default) or a protected
management network; use HTTPS for a remote admin endpoint. On a successful deploy
the application is registered with Caddy, which issues and renews the Let's
Encrypt certificate automatically. No certbot step is needed.
If `proxy.enabled` is false, deploys still run but no public URL is registered.

## Monitoring

The Monitoring tab shows CPU, memory and disk gauges plus a history chart per
server, pulled over the existing SSH/WinRM connections with no agent to install.
Configure the interval, timeout and retention under the `monitoring` section.
List the services to watch in each server's `services` field and the volume to
report in `disk_path`.

## Assistant

The Assistant tab answers questions from the curated guides plus live deploy and
monitoring data. Set `assistant.enabled: true` and point `assistant.chroma_url`
and `assistant.ollama_url` at your local ChromaDB and Ollama servers. If
ChromaDB is unreachable the assistant falls back to an in-process store; if
Ollama is unreachable it returns a grounded answer without the model.

## Rolling back a deployment

Open the Deployment tab, find the project, and click **Roll back**. The button
appears once the project has at least two successful deployments. Docker
rollback reuses the previous successful image tag without rebuilding; IIS
rollback restores the most recent timestamped backup and restarts the service
and application pool. Every rollback is recorded in deploy history.
